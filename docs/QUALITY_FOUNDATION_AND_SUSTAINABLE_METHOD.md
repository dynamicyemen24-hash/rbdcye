# منهجية الجودة المستدامة — رحماء بينهم

> هذه الوثيقة معيار تشغيل ومراجعة مستمر، وليست شهادة امتثال أو ادعاء بأن جميع الثغرات قد أُغلقت.

## الهدف

توحيد التجربة البصرية والسلوكية للموقع، وتحسين القراءة العربية واتجاه RTL، وإتاحة الاستخدام على الهواتف والأجهزة الصغيرة، مع تقليل التغييرات عالية المخاطر وحماية الوظائف الحالية.

## ما نُفّذ في هذه الدفعة

- إضافة `src/styles/quality-foundation.css` كطبقة عامة أخيرة في سلسلة CSS عبر `src/styles/index.css`.
- تعريف مقياس موحد للمسافات وهوامش الصفحة وعرض المحتوى ونصف قطر الزوايا وإيقاع القراءة.
- توحيد أساسيات صندوق العناصر، واحتواء الصور والوسائط، والتفاف النصوص الطويلة، وعرض الجداول القابل للتمرير عند الحاجة.
- تحسين وضوح التركيز المرئي للوحة المفاتيح، ومساحة التفاعل على الشاشات الصغيرة، وحجم حقول الإدخال لتقليل التكبير التلقائي على الهواتف.
- احترام تفضيل تقليل الحركة، وإضافة معالجة أولية لوضع التباين القسري.
- الإبقاء على تصميم المكونات الحالي والهوية اللونية، وتجنب إعادة كتابة صفحات التطبيق دفعة واحدة.

## المبادئ الحاكمة

1. **مصدر حقيقة واحد:** الرموز العامة في ملفات التصميم المركزية؛ لا تُنشأ ألوان أو مسافات جديدة عشوائيًا داخل المكونات.
2. **التدرج لا الهدم:** التغييرات العامة تضبط الثوابت فقط؛ أما تفاصيل المكوّن فتظل في ملفه المسؤول.
3. **RTL أولًا:** استخدم الخصائص المنطقية مثل `margin-inline` و`padding-inline` و`inset-inline` بدل ربط التصميم بجهة واحدة.
4. **الهاتف ليس نسخة مصغرة:** يجب اختبار 320 و360 و390 و768 و1024 و1440 بكسل، في الاتجاهين عند دعم ذلك.
5. **إمكانية الوصول جزء من الجودة:** لوحة المفاتيح، التركيز المرئي، التباين، أسماء العناصر، الرسائل والأخطاء، وتقليل الحركة.
6. **المحتوى الإنساني مسؤول:** لا تُنشر أرقام أثر أو شهادات أو أسماء مستفيدين أو نسب إنجاز دون مصدر وتاريخ وموافقة مناسبة. تُوسم البيانات التوضيحية بوضوح ولا تُعرض كحقائق.
7. **الأمان لا يُستنتج من CSS:** مراجعة المصادقة والصلاحيات والتحقق من المدخلات والـ webhooks والأسرار ومعدل الطلبات مسار مستقل واختباراته إلزامية.
8. **لا ادعاء بلا دليل:** لا تُعلن المطابقة أو الأداء أو إغلاق الثغرات قبل تنفيذ الاختبارات وتوثيق نتائجها.

## بوابات الجودة المطلوبة قبل الدمج

### 1. سلامة الكود
- `pnpm typecheck`
- `pnpm lint`
- `pnpm test`
- `pnpm build`
- إصلاح الإخفاقات الناتجة عن التغيير أو توثيقها قبل الدمج.

### 2. تجربة المتصفح
- اختبارات E2E للتنقل، والتبرع، والتواصل، وتسجيل الدخول، والواجهات الأساسية.
- مراجعة أخطاء Console وطلبات الشبكة الفاشلة وعدم وجود تمرير أفقي غير مقصود.
- اختبار القائمة على الهاتف، والنوافذ المنبثقة، والنماذج، والجداول، وحالات التحميل والفراغ والخطأ.

### 3. إمكانية الوصول
- فحص آلي عبر axe، ثم مراجعة يدوية بلوحة المفاتيح وقارئ شاشة عند الإمكان.
- تحقق من التباين، وترتيب التركيز، وتسميات الحقول، ورسائل الخطأ، وحالات التركيز، وتكبير النص حتى 200%.
- لا تعتمد نتيجة الفحص الآلي وحدها لإعلان الامتثال.

### 4. الأداء والاستقرار
- قياس Lighthouse على صفحة رئيسية وصفحة داخلية وصفحة تبرع، على جهاز محمول ومحاكاة شبكة بطيئة.
- متابعة مؤشرات Core Web Vitals ميدانيًا؛ الهدف الإرشادي عند الشريحة المئوية 75: LCP ≤ 2.5s، INP ≤ 200ms، CLS ≤ 0.1.
- قياس قبل/بعد بنفس الظروف، وعدم قبول تحسين بصري يسبب زيادة غير مبررة في حجم الحزمة أو زمن التفاعل.

### 5. الأمان والخصوصية
- مراجعة الصلاحيات على الخادم، والتحقق من المدخلات، وحماية CSRF عند انطباقها، وحدود المعدل، والتحقق من توقيعات webhooks، وسياسة CORS، والرؤوس الأمنية، وإدارة الأسرار.
- تنفيذ `pnpm audit --audit-level=high` ومراجعة النتائج وتحديث الاعتماديات بتغييرات قابلة للتراجع.
- عدم تسجيل بيانات المتبرعين أو المستفيدين الحساسة في السجلات أو أدوات التحليلات دون ضرورة وضوابط.

## ترتيب الأولويات

| الأولوية | أمثلة | معيار الإغلاق |
|---|---|---|
| P0 — حرجة | تسرب بيانات، تجاوز صلاحيات، مدفوعات مكررة، توقف التبرع | إصلاح واختبار أمني/وظيفي موثق |
| P1 — عالية | تعطل الهاتف، نموذج لا يُرسل، محتوى أساسي غير مقروء، فشل البناء | اختبار إعادة إنتاج ثم نجاح الاختبار بعد الإصلاح |
| P2 — متوسطة | عدم اتساق المسافات، ضعف التسلسل البصري، بطء غير حرج | قياس قبل/بعد ومراجعة بصرية |
| P3 — تحسين | حركة زخرفية أو تفاصيل تجميلية | لا تضر بالأداء أو إمكانية الوصول |

## سياسة المحتوى الواقعي

- كل رقم عن المستفيدين أو المشاريع أو التبرعات يرتبط بمصدر داخلي موثوق، وفترة زمنية، وتعريف لطريقة الحساب.
- كل قصة إنسانية تُراجع من حيث الموافقة والخصوصية وعدم كشف الهوية أو الموقع الحساس.
- لا تُستخدم عبارات «مضمون 100%»، أو «الأفضل عالميًا»، أو نسب أثر غير قابلة للتحقق.
- توضيح الرسوم والعملات ومراحل تنفيذ المشروع وسياسة الاسترداد والتواصل والشكاوى بلغة مباشرة.
- فصل المحتوى التحريري عن البيانات الحية، وإظهار تاريخ آخر تحديث للبيانات عند الحاجة.

## دورة الاستدامة

1. إنشاء Issue لكل عيب مع خطوات إعادة الإنتاج، والجهاز/المتصفح، والأثر، ومعيار قبول واضح.
2. إصلاح محدود النطاق في فرع مستقل، مع اختبار يغطي العيب.
3. تشغيل بوابات CI ومراجعة فرق بصري قبل الدمج.
4. نشر تدريجي مع خطة تراجع ومراقبة أخطاء الواجهة والخادم.
5. مراجعة شهرية للتبعيات والثغرات والأداء وإمكانية الوصول، ومراجعة ربع سنوية لتناسق المحتوى والتصميم.
6. تسجيل القرار والقياس في سجل تغييرات؛ لا يُغلق العيب بناءً على الانطباع فقط.

## حدود هذه الدفعة

هذه الدفعة تضيف طبقة CSS عامة قابلة للصيانة وتوثق معايير القبول. لم يتم في هذه الدفعة الادعاء بأن جميع الصفحات خضعت لمراجعة بصرية، أو أن الاختبارات والبناء والأمن اجتازت؛ يجب تشغيل بوابات الجودة أعلاه في بيئة المشروع قبل الدمج والنشر.
